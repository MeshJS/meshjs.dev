## createFacilitatorApp

Returns a [Hono](https://hono.dev) app exposing `GET /supported`, `POST /verify`, `POST /settle`. It holds no keys; it needs a provider for UTxO and slot queries and for broadcasting.

```ts
import { serve } from "@hono/node-server";
import { BlockfrostProvider } from "@meshsdk/provider";
import { chainStateFrom, createFacilitatorApp, InMemorySettlementStore } from "@meshsdk/x402";

const provider = new BlockfrostProvider("<BLOCKFROST_PREPROD_KEY>");
const readChain = chainStateFrom(provider);

const app = createFacilitatorApp({
  fetcher: provider,
  submitter: provider,
  store: new InMemorySettlementStore(),
  supportedNetworks: ["cardano:preprod"],
  resolveChainState: () => readChain(), // { protocol, currentSlot }
});
serve({ fetch: app.fetch, port: 8787 });
```

| Config | |
|---|---|
| `fetcher`, `submitter` | Mesh `IFetcher` and `ISubmitter` |
| `supportedNetworks` | Networks served |
| `resolveChainState(network)` | Live protocol parameters and tip slot |
| `store?` | `SettlementStore`. Default: in memory. |
| `supportedMethods?` | Default `["default", "masumi", "script"]` |
| `l1Confirmations?` | Range settled, advertised in `/supported`. Default `{ minimum: 0, maximum: 20 }`; `-1` is opt-in. |
| `allowMasumiDeployment?` | Approval hook for non-default Masumi deployments. Default: deny. |

## Endpoints

`POST /verify` and `POST /settle` take `{ paymentPayload, paymentRequirements }`. `paymentRequirements` must be the resource server's stored offer. Malformed bodies return `400 INVALID_PAYLOAD`.

`GET /supported` returns, per network, `extra: { assetTransferMethods, areFeesSponsored: false, l1Confirmations: { minimum, maximum } }`.

`/verify` returns `{ isValid: true }` or `{ isValid: false, invalidReason }`. `/settle` returns a `PaymentResponse`.

## Verification rules

| # | Rule | Error code |
|---|---|---|
| – | `accepted` equals the stored offer | `REQUIREMENTS_MISMATCH` |
| 1 | Every output address and the body `network_id` match the network | `INVALID_NETWORK` |
| 2–4 | An output pays `payTo` at least `amount` of exactly `asset` | `PAYTO_NOT_FOUND` |
| 5 | `nonce` is an input of the transaction | `NONCE_NOT_IN_INPUTS` |
| 5 | The nonce input and every other input are unspent | `NONCE_NOT_UNSPENT`, `INPUT_NOT_UNSPENT` |
| 6 | No mint, withdrawals, certificates, governance actions or donations | `UNSUPPORTED_TX_FEATURE` |
| 6 | Inputs = outputs + fee for lovelace and every asset; fee ≥ `minFeeA × size + minFeeB` | `VALUE_NOT_CONSERVED` |
| 7 | TTL is set, not passed, and not beyond `maxTimeoutSeconds` (slot-length aware) | `TTL_EXPIRED`, `TTL_TOO_FAR` |
| 8 | The `payTo` output meets min-UTxO | `BELOW_MIN_UTXO` |
| 9 | Confirmation threshold met (checked in `/settle`) | `settlement_pending` |

`extra.confirmationPolicy` outside -1..20 or outside the facilitator's range returns `INVALID_CONFIRMATION_POLICY`. `areFeesSponsored: true` is rejected.

**`script`**: `payTo` must carry the script credential derived from `script` plus `parameters`, or from `scriptHash` (`SCRIPT_ADDRESS_MISMATCH`). A Plutus V1 script with a datum is rejected (`SCRIPT_V1_WITH_DATUM`). The datum is not validated.

**`masumi`**: in addition, the facilitator enforces
- closed-object schema, `paymentType = Web3CardanoV2`, commitment digests, `terms.inputHash = inputCommitment.digest`;
- `termsDigest` recomputed and the seller's COSE signature verified, including `Blake2b-224(publicKey)` equal to the seller's payment-key credential;
- the escrow address derived from the canonical (or approved) deployment equals `payTo`, `signedTerms.contractAddress` and the address in `blockchainIdentifier`; exactly one output pays it;
- an inline datum in the 19-field `masumi.vested_pay.v2` layout with `FundsLocked`, empty `result_hash`, both cooldowns `0`, and no reference script; datum fields match the signed terms;
- the datum `buyer` controls the nonce input and its valid witness is in the transaction; `buyer`, `seller` and return addresses are key-credential addresses and the two payout targets differ;
- `lockedLovelace = requestedLovelace + collateral_return_lovelace`, collateral is `0` or at least 1,435,230, and the output clears min-UTxO after `SubmitResult`; the output holds exactly the requested asset;
- TTL on or before `pay_by_time`; the four deadlines keep the minimum intervals.

All Masumi failures use `MASUMI_*` codes.

## Settlement

`/settle` claims the transaction by its **canonical transaction id**, atomically, before broadcasting, then broadcasts once and observes the evidence.

| Situation | Response |
|---|---|
| Threshold met | `success: true`, `extra.status: "confirmed"`, actual `confirmations` |
| Policy `-1`, node accepted the broadcast | `success: true`, `extra.status: "mempool"`, `confirmations: -1` |
| Below threshold | `settlement_pending` with `transaction`; retry with the same payload resumes observing and never rebroadcasts |
| Same transaction already in flight or settled | `duplicate_settlement` |
| Validity window closed without the ledger recording it | `EXPIRED` (terminal) |
| Definitive ledger rejection | `submission_rejected: …`; the claim is released |
| Timeout or unknown node result | claim kept; reconciled by transaction id |
| Masumi: a different transaction for an already-claimed `termsDigest` | `MASUMI_TERMS_ALREADY_CLAIMED` |

A resumed retry must still carry the requirements the payment was made for (`REQUIREMENTS_MISMATCH` otherwise).

## SettlementStore

The default `InMemorySettlementStore` is not durable and does not evict. A multi-instance facilitator must implement `SettlementStore` on shared storage: `claim` must be an atomic insert-if-absent, and `bindTermsDigest` must atomically bind a digest to the first transaction id.

## Limits

- TTL and deadline conversion use the network's static slot configuration, not a live era summary.
- Phase-1 checks are the spec minimum (conservation, fee floor, unexplained-value rejection), not a full ledger validator.
- A non-empty Masumi `agentIdentifier` is checked only for the Masumi V2 registry policy prefix (`67ab0c92…bd0b`). The registry asset, seller authorization, metadata, endpoint and price are **not** validated on-chain. Use an empty `agentIdentifier` (unregistered seller) unless you validate these yourself.
- No limits on transaction size, datum size or commitment parts are enforced.
